# 从 0 到上线的软件开发全流程

这份手册按个人开发者或 2–4 人小团队的节奏编写。目标不是一次做完所有功能，而是在 4–6 周内上线一个可验证、可维护的 Android MVP。

## 0. 先决定“为谁解决什么问题”

在写代码前写出一页纸：

- 目标用户是谁，不服务谁。
- 用户今天怎么完成这件事。
- 最小闭环是什么。
- 哪些功能明确不上首发。
- 用什么行为证明产品有价值。

雪约的结论是：目标用户是需要往返雪场的滑雪人群；最小闭环是“车主发布 -> 乘客报价申请 -> 车主审核路线与价格 -> 成交后锁定座位并更新路线”；首发不做公开陌生人社交。

交付物：`docs/PRODUCT.md`、一页项目简介、成功指标。

## 1. 命名、商标与商店可用性

1. 列出 10 个候选名，检查是否容易读、容易打、容易在电话里说清。
2. 在中国商标网查相同/近似类别；商业项目应请专业代理复核。
3. 检查 Google Play、华为、小米、OPPO、vivo 等商店的名称占用。
4. 搜索域名与社媒账号，至少保留一个可运营入口。
5. 确认名称不会与现有知名 App、影视角色或敏感词冲突。

不要让“名称还没定”阻断原型，但**第一次上传商店前必须冻结名称和应用包名**。包名一旦发布，不能更改。

## 2. 写清 MVP 用户故事

建议每个故事写成：

```text
作为【需要去雪场的滑雪人】，
我想【按人数和上车点向顺路车主报价】，
这样【不用在多个群聊里反复找车和确认费用】。
```

雪约首发故事：

- 我能按出发区域、雪场和日期找到拼车。
- 我能查看当前有效路线、余座、雪具位和最低价格。
- 我能按人数和上车位置提交单人报价。
- 车主能查看加入后的路线、绕行时间与总报价。
- 车主能同意、拒绝或提出一轮回价。
- 我能接受回价或放弃，未成交不会占用座位。
- 成交后座位、价格和路线版本同步更新。
- 我重启 App 后还能看到本地创建的行程和申请。

每个故事附验收标准。例如“创建成功”必须包含：表单校验、保存成功、跳转详情、刷新后仍存在。

## 3. 画信息架构与关键流程

先画低保真线框，不先挑插画：

```text
首页 -> 找拼车 -> 路线详情 -> 提交报价
车主行程 -> 申请审核 -> 同意 / 拒绝 / 回价
发布 -> 设置余位、雪具位与最低价 -> 发布成功
行程 -> 我加入的 / 我发起的
我的 -> 隐私 / 安全 / 关于
```

检查每个页面：

- 用户为什么来到这里？
- 最重要的信息是什么？
- 这一页的下一步按钮是什么？
- 空状态、失败状态、加载状态分别是什么？

## 4. 定义品牌与设计系统

先确定 4–6 个色值、2 种字体角色、3 种圆角和一套间距，再写组件。设计 Token 放在 `src/theme.ts`。

必须提前确定：

- 主按钮和次按钮。
- 深色卡片与浅色卡片。
- 标题、正文、辅助文字三级字号。
- 选中/未选中/完成/错误状态。
- 图标尺寸与安全区。
- 触控区至少 44×44 px。

本项目设计规范见 `docs/BRAND.md`。

## 5. 技术选型

首发建议：**Expo + React Native + TypeScript**。

适合原因：

- 一套代码覆盖 Android/iOS/Web。
- Expo Router 提供文件路由和深链基础。
- EAS 可在云端生成签名 APK/AAB，不需要维护两台构建机。
- 需要使用原生能力时可 `prebuild` 或通过 config plugin 扩展。

如果产品强依赖复杂 3D、蓝牙或定制地图，应在原型阶段做技术验证；不要仅凭框架宣传选择。

## 6. 建立工程

```bash
npx create-expo-app@latest my-app --template blank-typescript
cd my-app
nvm use 22
npm ci
```

工程基线：

- `main` 分支始终可构建。
- 功能用 `codex/feature-name` 或 `feature/name` 分支。
- 每次提交只解决一个清晰问题。
- `.env*.local`、签名文件、服务账号 JSON 永不提交。
- CI 至少跑 lint、TypeScript 和 Android bundle 导出。

本项目已包含：

- `npm run lint`
- `npm run typecheck`
- `npm run doctor`
- `.github/workflows/quality.yml`

## 7. 数据与状态

MVP 用 AsyncStorage 保存行程数组，适合验证单机价值。需要同步后，迁移到服务端数据库，不把 AsyncStorage 长期当多人数据库。

状态设计规则：

- 统一业务模型放在 `src/types.ts`。
- 所有写操作通过 Provider/Store 暴露方法，不散落页面。
- 数据加载失败不能阻止 App 打开。
- 对未来云同步预留 `updated_at` 与冲突策略。
- 本地缓存必须有版本号，结构变更时迁移或回退。

## 8. 实现顺序

推荐顺序：

1. 主题、字体、图标和导航骨架。
2. 静态首页与详情，先把信息层级做实。
3. 真实状态与本地示例数据。
4. 创建表单和校验。
5. 清单、分享等闭环操作。
6. 空、错、加载状态。
7. 真机适配与性能。
8. 商店配置与物料。

不要先做登录、支付、首页动画。没有闭环时，这些都是延迟学习的成本。

## 9. 测试策略

### 开发自测

```bash
npm run lint
npm run typecheck
npm run doctor
npx expo export --platform android
```

### 手工验收矩阵

| 维度 | 必测 |
| --- | --- |
| 系统 | Android 最近两个大版本；如有 iOS 计划则加 iOS |
| 屏幕 | 360 px 小屏、390–430 px 主流屏、平板/大屏 |
| 字体 | 系统大字体、简中环境、含 emoji/长标题 |
| 输入 | 空表单、超长文本、中断返回、键盘遮挡 |
| 数据 | 首次启动、已有数据、损坏缓存、重启恢复 |
| 系统 | 返回键、分屏、深浅色、旋转锁定 |
| 操作 | 分享取消、连续点击、权限拒绝、无网络 |

### 发布前一票否决

- 崩溃或白屏。
- 创建后数据丢失。
- 展示虚假实时信息。
- 商店隐私声明与实际代码不符。
- 签名证书不可恢复。
- 应用包名、名称、图标或隐私政策缺失。

## 10. Android 构建与签名

本项目的完整命令、版本号和审核清单见 `docs/ANDROID_RELEASE.md`。

关键点：

- 开发包/内部测试使用 APK。
- 商店正式包使用 AAB。
- EAS 默认托管 Android keystore，必须备份并限制账户访问。
- 每次发布递增 `versionCode`；用户可见版本用 `versionName`。
- 首次上传 Google Play 后，包名不可更改。

## 11. 隐私、安全与合规

上线前逐项确认：

- App 实际收集哪些数据？MVP 只在本机保存内容。
- 引用了哪些第三方 SDK？每个 SDK 是否收集设备信息？
- 权限申请是否都对应可见功能？能不申请就不申请。
- 隐私政策是否能公开访问，且包含联系方式、数据用途、保存和删除方式。
- 删除本地数据/卸载行为是否在政策中说明。
- 面向中国境内分发时，是否满足 APP 备案与各商店的资料要求。

不要在未使用时后台申请定位、通讯录、相册或通知权限。地图、推送、统计 SDK 一旦加入，必须重新更新隐私政策和 Data Safety。

## 12. 商店物料

最低准备：

- 512×512 商店图标。
- 至少 2 张、建议 4–8 张真实手机截图。
- 1024×500 横图。
- 30 字以内名称。
- 80 字以内短描述。
- 4000 字以内完整描述。
- 隐私政策 URL。
- 内容分级、目标人群、数据安全表。
- 发布说明和新版本测试账号（如需要）。

本项目文案模板见 `docs/STORE_LISTING.md`。

## 13. 上线流程

1. 冻结版本，提交 Git tag，例如 `v1.0.0`。
2. 生成 Release AAB。
3. 上传 Google Play 内部测试；如个人账号有封闭测试要求，按当前 Play Console 指引完成。
4. 安装真实商店构建，做 24 小时冒烟和关键路径回归。
5. 提交内容分级、数据安全、广告声明和隐私政策。
6. 分阶段发布：5% -> 20% -> 50% -> 100%。
7. 关注崩溃、启动、创建和分享漏斗。
8. 每周检查商店评论和崩溃聚合。

国内商店需分别提交，不能把 Google Play 的隐私与备案材料直接照搬。渠道资料、SDK 清单、签名和版本策略要统一管理。

## 14. 发布后迭代

按证据排序，而不是按“想做”排序：

1. 阻断性问题。
2. 创建/分享漏斗损失。
3. 高频用户反馈。
4. 留存相关的小功能。
5. 视觉润色与增长实验。

每 2 周复盘：

- 哪个功能真正被使用？
- 哪个页面掉出最多用户？
- 哪些反馈重复出现？
- 下一版删除什么，而不只是增加什么？

## 建议排期

| 周 | 重点 | 结果 |
| --- | --- | --- |
| 第 1 周 | 用户、命名、MVP、线框 | 可评审的产品与品牌方向 |
| 第 2 周 | 工程、导航、核心页面 | 静态可点击原型 |
| 第 3 周 | 创建、持久化、分享、清单 | 完整单机闭环 |
| 第 4 周 | 测试、修复、商店素材 | 可提交内部测试 |
| 第 5 周 | 审核、隐私、备案、渠道 | 可进入商店审核 |
| 第 6 周 | 灰度、监控、反馈 | 稳定首发版本 |

如果时间紧，先砍视觉润色和“我的”统计，不砍数据安全、隐私声明和真机回归。

## 常用排障

环境依赖异常：

```bash
nvm use
npm ci
npx expo-doctor
npx expo install --fix
```

构建缓存异常：

```bash
npx expo start --clear
```

Android 原生目录不存在是正常的：本项目使用 Continuous Native Generation。修改原生配置应改 `app.json` 或 config plugin，然后重新 prebuild，不要手改生成目录再期待下次构建保留。
